================================================================================
M5 — READ PATH AND REST SURFACE
Guide for PR18, PR19, PR20, PR21, PR22.
Read alongside docs/BUILD-PLAN.md section 6.6.
================================================================================

GOAL OF THIS MILESTONE
  Build the read side, which deliberately does not go through the domain, and
  make the HTTP surface behave the way a REST API is supposed to: paged,
  filterable, cacheable, versioned, and optionally hypermedia-driven.

RULES THAT APPLY TO ALL FIVE PRs
  - No aggregate and no repository on the read path. Query handlers use
    DbContext directly with AsNoTracking and project into a DTO.
  - Select into the DTO, never load the entity and map afterwards. The
    projection becomes SQL and the database returns only the needed columns.
  - Anything user-supplied that reaches an OrderBy or a filter goes through a
    whitelist. String interpolation into a query is how injection happens.
  - Every PR follows the seven-step loop in BUILD-PLAN.md section 7.

PR20 — feat/http-caching
================================================================================

STEP 1  Branch
    git switch main
    git pull
    git switch -c feat/http-caching

STEP 2  The distinction worth getting right
    Expiration model: the client may reuse a response for N seconds without
    asking. Validation model: the client asks, and the server answers 304 if
    nothing changed. This PR implements validation, because user data changes
    unpredictably and a stale user record is a real problem.

STEP 3  Files
    src\UserManagementAPI.Api\Caching\ETagGenerator.cs
        A stable hash of the serialized response body. Stable means the same
        payload always produces the same tag — no timestamps, no GUIDs.

    src\UserManagementAPI.Api\Filters\ETagFilter.cs
        An IAsyncResultFilter. On the way out, compute the ETag and set the
        header. If the request carried If-None-Match and it matches, replace
        the result with 304 and an empty body.

    Apply to GET endpoints only. A 304 on a POST is meaningless.

STEP 4  Verify by hand
    Call GET /api/v1/users/{id}, copy the ETag, call again with
    If-None-Match set to that value, and confirm a 304 with no body.
    Then change the user and confirm the ETag changes.

STEP 5  Tests
    Identical payloads produce identical ETags.
    A matching If-None-Match returns 304 with an empty body.
    A stale If-None-Match returns 200 and the new payload.

STEP 6  Commit, push, PR, merge, clean up.

DEFINITION OF DONE
    Conditional GET works on every read endpoint and is covered by tests.

PR21 — feat/api-versioning
================================================================================

STEP 1  Branch
    git switch main
    git pull
    git switch -c feat/api-versioning

STEP 2  Packages
    dotnet add src\UserManagementAPI.Api package Asp.Versioning.Mvc
    dotnet add src\UserManagementAPI.Api package Asp.Versioning.Mvc.ApiExplorer

STEP 3  Work
    URL-segment versioning, which the routes already assume: /api/v{version}/.
    Report supported versions in the response headers.
    Group each version separately in the OpenAPI document so Scalar shows them
    apart.

    Then demonstrate that the versioning is real rather than decorative: add a
    v2 of one endpoint whose response shape genuinely differs — for example a
    UserDto v2 that returns a single displayName instead of separate first and
    last names. v1 keeps working, untouched.

    This is the payoff for keeping HTTP contracts separate from commands in M3
    PR12: the v2 contract changes and neither the command nor the domain moves.

STEP 4  Tests
    v1 and v2 of the same route both resolve and return their own shapes.
    An unsupported version returns 400.

STEP 5  Verify, commit, push, PR, merge, clean up.

DEFINITION OF DONE
    Two versions coexist, documented separately, with no change to the domain.

PR22 — feat/hateoas
================================================================================

STEP 1  Branch
    git switch main
    git pull
    git switch -c feat/hateoas

STEP 2  Why it is opt-in
    Hypermedia links are useful to a client that discovers the API and noise to
    a client that does not. Putting them behind a custom media type means the
    default response stays a plain, predictable JSON object and the richer
    representation is available on request.

STEP 3  Files
    src\UserManagementAPI.Api\Hateoas\
        Link.cs                  href, rel, method
        LinkedResource.cs        wraps a payload with its links
        UserLinkGenerator.cs     builds self, update, lock, assign-role links,
                                 using LinkGenerator so URLs are never
                                 hand-built strings
    src\UserManagementAPI.Api\Filters\ValidateMediaTypeAttribute.cs
        Reads the Accept header, sets a flag on HttpContext.Items, returns 406
        on an unsupported custom media type.

    Media type: application/vnd.umapi.hateoas+json

STEP 4  Root document
    src\UserManagementAPI.Api\Controllers\V1\RootController.cs
        GET /api — returns links to the top-level resources, so the API is
        discoverable from one entry point.

STEP 5  OPTIONS and HEAD
    OPTIONS /api/v1/users returns an Allow header listing the supported methods.
    HEAD on the read endpoints returns the headers of the GET with no body.

STEP 6  Tests
    Without the custom Accept header the response is plain JSON with no links.
    With it, the links are present and each href resolves.
    An unknown vendor media type returns 406.

STEP 7  Verify, commit, push, PR, merge, clean up.

STEP 8  Close the milestone
    git tag -a v0.6.0 -m "M5: read path and REST surface — projections, paging, caching, versioning, hypermedia"
    git push origin v0.6.0

DEFINITION OF DONE FOR M5
    Read endpoints project directly to DTOs.
    Collections page, filter, search and sort with a whitelist.
    Conditional GET returns 304.
    Two API versions coexist.
    Hypermedia is available and opt-in.

    0013  HATEOAS behind an opt-in media type

    Also worth an ADR of its own if you deviate: the decision NOT to implement
    data shaping. Reflection over ExpandoObject means the response no longer
    matches the OpenAPI schema and the client loses its types. In 2026 that is
    a cost, not a feature. Record the reasoning — deliberately leaving something
    out, with a reason, reads better than implementing it because a tutorial did.
