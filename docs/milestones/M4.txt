================================================================================
M4 — AUTHENTICATION AND AUTHORIZATION
Guide for PR14, PR15, PR16, PR17.
Read alongside docs/BUILD-PLAN.md sections 6.7 and 6.8.
================================================================================

GOAL OF THIS MILESTONE
  Issue and validate credentials, rotate refresh tokens safely, and gate every
  mutating endpoint on a specific permission. By the end, [Authorize] alone
  appears nowhere — every protected action names the permission it requires.

RULES THAT APPLY TO ALL FOUR PRs
  - No password, token or hash is ever logged, returned in an error, or written
    to the audit trail.
  - No secret is committed. Signing keys live in user-secrets locally and in
    environment variables everywhere else.
  - Hashing belongs to Infrastructure. The domain holds a PasswordHash value
    object and knows nothing about the algorithm.
  - Every PR follows the seven-step loop in BUILD-PLAN.md section 7.

PR14 — feat/auth-login
================================================================================

STEP 1  Branch
    git switch main
    git pull
    git switch -c feat/auth-login

STEP 2  Packages
    dotnet add src\UserManagementAPI.Infrastructure package Konscious.Security.Cryptography.Argon2
    dotnet add src\UserManagementAPI.Api package Microsoft.AspNetCore.Authentication.JwtBearer

STEP 3  Secrets
    cd src\UserManagementAPI.Api
    dotnet user-secrets set "Jwt:SigningKey" "<at least 64 random characters>"
    dotnet user-secrets set "Jwt:Issuer" "usermanagementapi"
    dotnet user-secrets set "Jwt:Audience" "usermanagementapi"
    cd ..\..

STEP 4  Files
    src\UserManagementAPI.Application\Abstractions\IPasswordHasher.cs
        Hash(string) and Verify(string password, string hash).

    src\UserManagementAPI.Infrastructure\Identity\Argon2PasswordHasher.cs
        Argon2id. Random salt per password, stored with the hash. Parameters
        from configuration, not literals, so they can be raised as hardware
        improves. Record the chosen memory, iteration and parallelism values
        and the reason in the PR description.

    src\UserManagementAPI.Application\Abstractions\ITokenService.cs
        CreateAccessToken(User, IReadOnlyCollection<string> permissions).

    src\UserManagementAPI.Infrastructure\Identity\JwtTokenService.cs
        Short-lived access token, 15 minutes. Claims: subject, email, and one
        claim per permission code. Roles are not put in the token — permissions
        are what the policies check.

    src\UserManagementAPI.Application\Auth\Commands\Login\
        LoginCommand, handler, validator.
        The handler must take the same time whether the email exists or not,
        and must return one generic error for both a wrong email and a wrong
        password. A distinguishable response is a user-enumeration hole.

    src\UserManagementAPI.Api\Controllers\V1\AuthController.cs
        POST /api/v1/auth/login

    Program.cs
        AddAuthentication with JwtBearer, validating issuer, audience,
        lifetime and signing key, with zero clock skew.
        UseAuthentication and UseAuthorization are already in the pipeline in
        the right order from M0 PR3.

STEP 5  Verify
    Run the API, log in through Scalar with the seeded administrator, paste the
    token into jwt.io and confirm the claims are what you expect.

STEP 6  Tests
    Correct credentials return a token; wrong password and unknown email return
    the same error.
    A locked or deactivated user cannot log in.
    Hash and verify round-trip; two hashes of the same password differ, because
    the salt differs.

STEP 7  Commit, push, PR, merge, clean up.

DEFINITION OF DONE
    Login works. Responses do not reveal whether an email is registered.

PR15 — feat/auth-refresh-rotation
================================================================================

STEP 1  Branch
    git switch main
    git pull
    git switch -c feat/auth-refresh-rotation

STEP 2  The model
    RefreshToken is its own aggregate, not part of User. It rotates on every
    refresh; putting it inside User would load and lock the entire user object
    on every token exchange.

    Only the hash of the token is stored. A database leak must not yield usable
    tokens.

    replaced_by records the rotation chain. That column is what makes theft
    detectable: if a token that was already exchanged is presented again, the
    chain is compromised, so revoke every token for that user rather than only
    the one presented.

STEP 3  Files
    src\UserManagementAPI.Domain\Auth\RefreshToken.cs
        Issue, Rotate, Revoke. IsActive computed from expiry and revocation.

    src\UserManagementAPI.Domain\Auth\IRefreshTokenRepository.cs
    src\UserManagementAPI.Infrastructure\Persistence\Repositories\RefreshTokenRepository.cs
    src\UserManagementAPI.Infrastructure\Persistence\Configurations\RefreshTokenConfiguration.cs
        Index on token_hash. Index on user_id for bulk revocation.

    src\UserManagementAPI.Application\Auth\Commands\RefreshToken\
    src\UserManagementAPI.Application\Auth\Commands\Logout\

    Migration
        dotnet ef migrations add AddRefreshTokens `
          --project src\UserManagementAPI.Infrastructure `
          --startup-project src\UserManagementAPI.Api

    Endpoints
        POST /api/v1/auth/refresh
        POST /api/v1/auth/logout

STEP 4  Tests
    A refresh returns a new pair and marks the old token replaced.
    Presenting an already-rotated token revokes the whole chain and fails.
    An expired token fails.
    A revoked token fails.
    Integration test over the full cycle: login, refresh twice, replay the
    first token, confirm every token for that user is now dead.

STEP 5  Verify, commit, push, PR, merge, clean up.

DEFINITION OF DONE
    Rotation works and reuse detection is proven by a test, not by comment.

PR16 — feat/authz-permissions
================================================================================

STEP 1  Branch
    git switch main
    git pull
    git switch -c feat/authz-permissions

STEP 2  Why permissions rather than roles
    A role check hard-codes an organisational decision into the code: change who
    may do a thing and you redeploy. A permission check names the capability;
    which role holds it is data. Roles remain, as containers of permissions.

STEP 3  Files under src\UserManagementAPI.Api\Authorization\
    PermissionRequirement.cs        Carries the permission code.
    PermissionAuthorizationHandler.cs
                                    Reads permission claims from the principal.
    PermissionPolicyProvider.cs     Builds a policy on demand from the code, so
                                    every permission does not need registering
                                    by hand.
    HasPermissionAttribute.cs       [HasPermission("users.write")]

STEP 4  Apply to every endpoint
    Go through UsersController, RolesController and AuthController and give each
    action the permission it needs. Login and refresh stay anonymous.
    When this PR is done, no bare [Authorize] should remain in the project.

STEP 5  Tests
    A principal without the permission gets 403, with it gets 200.
    An unauthenticated request gets 401, not 403.
    Functional test: log in as the seeded Member and confirm a write endpoint
    returns 403.

STEP 6  Verify, commit, push, PR, merge, clean up.

DEFINITION OF DONE
    Every mutating endpoint names its required permission. Nothing relies on a
    role name in code.

PR17 — feat/audit-log
================================================================================

STEP 1  Branch
    git switch main

    git switch -c feat/audit-log

STEP 2  Files
    src\UserManagementAPI.Api\Services\CurrentUser.cs
        Implements ICurrentUser from IHttpContextAccessor. Registered in
        Program.cs.

        Id, ActorId, Action, Entity, EntityId, Payload as jsonb, AtUtc.

    src\UserManagementAPI.Infrastructure\Auditing\AuditInterceptor.cs
        A SaveChangesInterceptor that records who changed what. Append only —
        no update path, no delete path.

    Payload rules
        Never write a password, a token or a hash into the payload. Write which
        fields changed, not their before-and-after values, for anything
        sensitive.

    Migration
        dotnet ef migrations add AddAuditLog `
          --project src\UserManagementAPI.Infrastructure `
          --startup-project src\UserManagementAPI.Api

STEP 3  Tests
    An authenticated write records the acting user id.
    A system write with no principal records null rather than failing.
    No audit payload contains a password or token field. Assert this — it is
    the kind of thing that regresses silently.

STEP 4  Verify, commit, push, PR, merge, clean up.

STEP 5  Close the milestone
    git tag -a v0.5.0 -m "M4: authentication and authorization — JWT, refresh rotation, permission policies, audit log"
    git push origin v0.5.0

DEFINITION OF DONE FOR M4
    Login, refresh, rotation with reuse detection, and logout all work.
    Every protected endpoint names a permission.
    Every write is attributable to an actor.
